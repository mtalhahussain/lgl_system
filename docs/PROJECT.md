## Core workflows and invariants

1. Admin creates courses, Teachers and batches, then admits a Student. Admission locks the batch, checks duplicate/capacity eligibility, and creates the enrollment and schedule atomically. Later course price edits do not rewrite fee agreements.
2. Gross less discount is the exact net agreement. Support one installment, up to 12 equal monthly installments with deterministic remainder and safe month-end dates, or custom amounts/dates summing exactly to net. Money uses integer minor-unit calculations and DECIMAL storage.
3. Admin posts cash/bank/card/JazzCash/Easypaisa as recorded payment methods. Partial/early payment allocates against debt. Reject overpayment and unreconciled legacy balances. Lock the enrollment, validate the unique submission key/payload, and create payment, allocations, unique receipt and audit atomically. An identical retry returns the same receipt; conflicting reuse fails.
4. Posted payments and allocations are immutable. Admin may fully reverse once with reason and actor; preserve originals and restore debt. Collections report records payments in their payment period and negative reversals in their reversal period. Receipt snapshots preserve identity, course/batch, institute, currency and timezone. Currency freezes once payments exist.
5. Transfer only between same-course batches with capacity and no financial activity. Link the retained source to its target, move the schedule once and avoid duplicate debt. Withdrawal retains agreement, debt, payment history and a reason; it does not issue a refund.
6. Teacher or Admin marks eligible Students for a session, never a future date. Blank stays unmarked. Corrections require a 5–1000 character reason and audit. Attendance percentage is `(present + late) / (present + late + absent)`; excused/cancelled records are excluded and an empty denominator has no percentage. Show completeness separately. Historical eligibility accounts for completed/dropped/transferred enrollment dates.
7. Student views only their own portal and receipts. Password change requires the current password. Account/profile input cannot escalate role or active state. Deactivation/cancellation preserves history.

Lists/reports paginate. Responsive menus, keyboard navigation and printable HTML receipts/reports reuse existing layouts. Collection printing clearly describes current-page rows versus full-period totals. No mandatory PDF/Excel package is needed; browser QA generated a print PDF as evidence only.

## Multi-level package (A1 + A2, A1 to B1, A1 to B2)

Admin can choose Enrollments > Multi-level package instead of normal single-module admission. One existing active Student takes 2–4 consecutive CEFR levels (A1, A2, B1, B2, C1, C2 order; no gaps). Every batch must already exist, be open with capacity, and belong to an active course; each next batch must start after the previous one ends. Seats for later levels are reserved now; there is no automatic promotion. Multiple batches per level (different timings, teachers, online/on-site) are chosen per level; timing is identified by the batch name at the owner's choice.

Admin enters the package price for each sale; this is how both the standard package discount and any student-specific discount are given. The price must be positive and not above the normal course fees total. It is split across levels in proportion to normal fees using integer minor units (nearest cent; the last level takes the exact remainder), so each enrollment stores its normal fee and allocated discount. Example: fees 35,000.00 + 35,000.01 + 40,000.00 + 39,999.99 at price 120,000.00 give 28,000.00, 28,000.01, 32,000.00 and 31,999.99.

Payment plan: "full" records the whole price now (method required) through canonical PaymentService postings, one per level; "installments" (2–12 per level) creates equal monthly installments for each level's share starting at that level's start date (or today if it has started) and posts nothing; installments are later collected and receipted from the fee ledger like any module payment.

The service locks batches in ID order, the Student and course rows, then reuses canonical admission and payment services within one transaction. The immutable enrollment_packages row snapshots identity, currency/timezone, plan, installment count, normal total, discount total and per-level course/batch/dates/fees/discount/share/installments and payment IDs (full plan). `method` stores the tender for full plans and `installments` otherwise. enrollments.enrollment_package_id keeps the association with a restrictive foreign key. A unique submission key and payload make retries return the original record; conflicting reuse fails. Collections and dashboards count module payments only; the package page is a receipt (full) or agreement (installments), never another collection. Admin and the owning Student can view it; Teachers and unrelated Students cannot.

Package level discounts cannot be edited separately. For a full plan, reversing any original level payment reverses all of them atomically under package/enrollment locks; any reconciliation failure rolls back the whole reversal. Installment-plan payments reverse individually. This is payment correction, not package cancellation or refund. Package cancellation/refund pricing and sales without scheduled later-level batches remain future scope.

Migration 2026_11_03_000001_create_enrollment_packages_table adds the table and nullable enrollment link; the multi-level change needed no further migration. Older A1 + A2 records (no plan field) display as full-payment receipts.
## Hikvision attendance machine (push)

The app runs on the VPS; a Hikvision face + fingerprint terminal on the institute LAN pushes access events with "HTTP Listening" to `POST /biometric/hook/{token}` (routes/biometric.php: no web group, session, cookies or CSRF; throttled; 32–64 character random token per machine, regenerable). Unknown tokens get 404; known machines always get 200 OK so the terminal does not resend in a loop. Inactive machines update last contact but store nothing. No device password is stored and the server never calls the machine; faces and fingerprints are enrolled on the terminal or iVMS-4200.

`HikvisionDriver` accepts raw JSON or multipart `event_log`/`AccessControllerEvent` parts, ignores face pictures, and keeps only access-granted sub-events (config/biometric.php: 1 card, 38 fingerprint, 75 face). Times become wall-clock in the app timezone using the machine's time zone. Each person's `users.device_employee_no` (Machine Employee No.; letters/digits, unique index) is the Employee No. on the terminal.

`ClassPunchRecorder` stores every punch once in immutable `biometric_punches` (unique machine + employee no. + time) with a result: present, late, already_marked, no_session, teacher, unknown_code, ignored or clock_ahead (more than 10 minutes ahead of the server). For an active Student it finds today's non-cancelled session of a batch where the Student is eligible, from 30 minutes before start (`BIOMETRIC_EARLY_MINUTES`) until end; on or before start + the session's late minutes (default 15) is Present, after is Late. It creates the attendance with `auto_marked`, machine id and check-in time plus an `attendance.device_marked` audit row with no actor. It never overwrites an existing record and never marks Absent; teachers/Admin still mark absentees and corrections follow the normal reason rule. Teacher punches are only logged; Admin > Teacher Attendance shows first and last punch per day. Payroll is not affected.

Admin > Settings > Integrations > Attendance machine adds/edits machines, shows setup steps with the push URL, last contact, today's KPIs and a filterable punch log with CSV. Session pages show "Machine HH:MM" on machine-marked rows. Teachers and Students have no access to these pages. Migration 2026_11_03_000002_create_biometric_tables adds the two tables and an index on users.device_employee_no; rollback refuses.

### Automatic machine numbers and user sync (bridge PC)

Every active Student/Teacher gets a Machine Employee No. automatically (`BiometricCode`, adapted from the gym project: the user id, or the highest numeric number + 1 when the id is taken). Admin may type a number on the form; empty keeps the current one. User created/updated events (`MachineUserSync`) keep `biometric_device_users` (one row per machine and employee number: action upsert/delete, status pending/synced/failed, version, attempts, last error) in step: new eligible user or name change → upsert; number change → delete old + upsert new; deactivation or role change → delete; reactivation → upsert. Adding a machine or "Send all users again" queues every active Student/Teacher.

The VPS cannot reach the LAN machine, so an always-on institute Windows PC runs `scripts/hikvision-bridge.ps1` (PowerShell 5.1, Task Scheduler every minute, single-instance). It reads a per-machine JSON config downloaded from Admin (server URL and a separate `bridge_token`; the Admin fills in the machine URL/user/password, which stay on that PC). Each run: `GET /biometric/bridge/{token}/pending` (50 rows; failed rows retried after 10 minutes, up to 20 attempts), apply over ISAPI with digest login (`UserInfo/SetUp`, falling back to `Record`/`Modify`; delete via `UserInfo/Delete`, falling back to `UserInfoDetail/Delete`; already-missing counts as done), then `POST .../results`. A result only applies when the row version still matches, so a change made meanwhile is sent again. Names are cut to 32 characters. Faces/fingerprints are still enrolled on the terminal. Admin > Attendance Machine shows synced/waiting/failed counts, failed errors, bridge last contact, setup steps and downloads, and can regenerate the bridge key.

Migration 2026_11_03_000003_create_biometric_device_users_table makes `users.device_employee_no` unique (refusing with the duplicate numbers listed), adds `bridge_token`/`bridge_seen_at` and the sync table; rollback refuses. The unused gym files (ZKTeco/generic drivers, ADMS command queue, driver registry/contract, gym punch processor, API push/sync controllers), the old pull-mode HikvisionAttendanceService, the unrouted StudentController fingerprint methods and the unused legacy attendance create view were removed at the owner's request; old fingerprint columns remain.

## WhatsApp fee reminders (Meta Cloud API)

Reuses the gym project's Cloud API sender (`WhatsAppService`, approved template messages). Secrets are only `.env` values `WHATSAPP_TOKEN` and `WHATSAPP_PHONE_NUMBER_ID` (plus optional `WHATSAPP_VERSION`, `WHATSAPP_DEFAULT_COUNTRY_CODE`=92); they are never stored in the database or shown. Admin > Settings > Integrations > WhatsApp fee reminders holds the on/off switch (off by default), days before the due date (default 3, 0 = none), "also on the due date" (default on), template name (default `fee_reminder`) and language (default `en`), setup steps with suggested template text, a test send and the message log with filters/CSV.

The template has five body variables: 1 student name, 2 outstanding installment amount, 3 due date, 4 course · batch, 5 institute name. `fees:whatsapp-reminders` (daily 10:00, synchronous, no queue worker) sends for each installment with an allocation-derived outstanding balance due in N days ("before_due") or today ("due_today"), on active/completed enrollments of active Students. A unique `kind:installment` key is claimed before calling Meta, so each automatic reminder goes once even if the command runs twice; failures are logged and not retried automatically. Only the Student's profile phone is used; local 03xx numbers become 923xx and invalid numbers are logged as failed without an API call. Fee Management shows Admin a "Send WhatsApp reminder" button per enrollment with debt: it targets the earliest unpaid installment, at most once per installment per 24 hours. Every attempt is an immutable `whatsapp_messages` row (only status/provider id/error are written after the call) with student, enrollment, installment, kind, phone, template, parameters, status, Meta message id, error and sender. Delivery/read webhooks, overdue repeats and guardian numbers are not included.

Migration 2026_11_03_000004_create_whatsapp_messages_table adds the log and the five `whatsapp` settings; rollback refuses. The old deferred email `fees:send-reminders` command and FeeReminderNotification were replaced.

## Automatic batch timetable and teacher attendance (S03)

Batch creation/update, weekly schedule writes and automatic class creation share a transaction and batch lock. Automatic work is limited to five years and 1000 new classes per save; invalid ranges or limits roll back the entire save. Multiple slots on an empty date are supported; duplicate weekday/start rows are rejected. Past/completed/cancelled batches receive no automatic classes. Leaving the schedule empty keeps legacy/manual batches usable. No migration or automatic backfill runs on deployment; Admin may save an existing scheduled batch to fill missing future dates.

Teachers see batch start/end dates and weekly timings on their dashboard, My Batches and course batch lists. Today’s classes expose direct attendance links, scoped to the assigned teacher. Regular dates are automatic; manual creation is labelled Extra / makeup class. Bulk generator controls remain available under Advanced on Admin batch pages; existing scoped generator endpoints retain their previous authorization for compatibility. Existing class times, cancellations and attendance are never silently rewritten by schedule edits.

## Class teaching records and makeup coverage (S05)

An additive forward-only migration adds nullable teaching outcome, start/confirmation times, recorder, reason and a restricted self-reference for makeup classes. Existing completed sessions are not backfilled as Taken: student attendance may already have completed their generic status. Teacher/Admin explicitly records Taken or Missed; dates must be today or earlier. Missed requires a 5–1000 character reason and no existing student attendance. Its underlying status becomes cancelled, preserving the row and excluding it from student absence/completeness calculations and machine attendance matching. Teacher confirmation is self-reported, not machine proof. In-person class details separately show the assigned teacher’s machine-punch count and first/last times for that date. No device/provider contact occurs.

Makeup is created from an original missed class in the same non-cancelled batch, including a completed batch when a late makeup is needed. Source and batch locks serialize duplicate creation; one pending or taken makeup is permitted. A conflicting same-date/start slot is rejected. The original date/reason remains unchanged. Coverage is derived as Needed, Pending or Covered; only explicit Taken on a linked makeup makes it Covered. Cancelled or missed makeup rows remain in history, and a replacement can be linked from the original missed row. No makeup chains are allowed. Linked makeup details and recorded outcomes are protected from generic editing; an unconfirmed makeup can be cancelled and replaced. Student attendance is recorded separately on the actual makeup date. These records do not change payroll or financial agreements.

## Unpaid batch correction (A05)

Admin can correct an individual active unpaid admission to an available upcoming/ongoing batch of the same course through the enrollment detail page. The existing transactional transfer boundary locks batches in ID order and the source enrollment, preserves the original linked record and moves installments exactly once. Correction requires a 5–500 character reason, retains the original admission date and fee agreement, and records an additional enrollment.batch_corrected audit. Any posted payment history (including reversed payments), refunds, package membership, source/target student attendance or exam results, or a certificate for that course level blocks correction. Target course must remain active; duplicate target enrollments and capacity violations are rejected. Different-course/level corrections and paid corrections remain unsupported.
